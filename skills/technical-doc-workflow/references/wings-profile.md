# Wings 代码讲解稿的可选规范

仅在用户选择沿用 Wings 历史讲解规范时使用。本文件不把历史章节号和模块数量推广为其他文档的固定要求。以本轮指定模板和工作稿为准；新模板可能将同类内容放在不同章节。

## 整体内容关系

背景说明业务问题与价值，设计方案说明整体思路，代码目录建立源码分布认识，核心实现章节解释关键机制，效果案例与专利说明承接相应依据。模板要求保留的章节按用户选择执行；不在格式任务中补造客户案例、性能结果或专利关联。

## 代码目录部分（历史 3.4）

- 目录说明按组件和职责组织，保留用户需要的目录，只减少非核心文件的展开。
- 控制与编排、加速交付等组件分别说明；用关键入口文件辅助定位，不逐一罗列所有文件。
- 用户指定的重要入口（例如启动脚本、控制入口、安装入口）保留。版本目录、文档资料、插件和模板等是否展开依照本轮要求。
- 本节负责“代码在哪里、各部分做什么”，函数协作与关键实现留给核心实现章节。

## 总流程部分（历史 4.1）

- 从部署输入、配置与场景决策、脚本交付、服务运行到请求处理建立完整链路，依据实际范围选择分段。
- 总流程与后续子模块是包含关系，名称和职责一致；总览中的核心步骤应在后文找到对应展开。
- 保留理解链路所需的关键分支；准入门、排队、释放等内部细节在所属模块展开。
- 总览图和流程描述保持对应，不把只负责生成脚本的控制端画成实际执行引擎推理的组件。

## 创新点子章节

技术机制名称放在前面，能力名称（如“四个永”）放在括号中；模块数量和名称服从当前稿件。

默认内部顺序：**创新点简述 → 伪代码 → 代码位置 → 真实代码简写 → 代码说明**。一个创新点通常配一幅图，图放在所属模块附近。

- 简述说清解决的问题、核心机制和作用，不重复大段背景。
- 伪代码从功能层面凝练，有关键变量、必要条件和失败边界；参数处理类模块可体现参数结构的连续变化，而非只列“读取、合并、启动”。
- 代码位置按支撑该机制的目录、文件与函数给出，可跨文件联动。
- 真实代码保留核心函数骨架和必要分支，非核心参数或语句可省略；保留行的内容和函数归属必须真实。不要为了精简只留某个分支，导致与伪代码不对应。
- 代码说明解释关键实现与设计目的，紧接对应示例。避免将一个模块的伪代码和实际代码拆到不相邻位置。
- 不额外强制添加步骤表、对应表或重复小结；用户所选模板明确要求时再添加。

## 图示关系

每个模块的图与总览图保持一致的视觉风格。保留输入输出、核心组件以及必要交互，在中间组件内表达关键处理逻辑。使用真实函数名时，同时给出可读的职责说明，区分内部调用、返回值和外部交互。

图中文字保留主次；删除次要步骤前先核对总流程和源码，避免破坏必要分支。代码静态核对、实际运行验证和效果证明分别表述。

## Word

优先使用用户指定历史 Word 作为参考；没有参考时采用通用 Word 默认值。代码使用 Consolas＋宋体 9.5 pt；避免代码自动折行和无必要的大块留白。是否保留末页横向、生成全文纵向替代版或打包 ZIP，由用户当前要求决定。
