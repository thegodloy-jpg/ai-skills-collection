# 技术文档：先迭代 MD，再生成 Word

## 工作约定

- Markdown 是正文和结构的编辑基准。默认在 MD 阶段工作，直到用户明确要求生成 Word。
- “MD 已定稿”表示保留该版本；“把这份转成 Word”已经足够启动转换，不再要求额外确认。用户也可明确要求从当前草稿导出审阅版 Word。
- 从会话和用户指定路径确定工作稿，不凭修改时间或文件名中的版本号自动换稿。多个候选仍无法判断时，只询问影响工作的缺失信息。
- 本轮明确要求优先，沿用此前仍有效的决定。模板、项目规则与默认参数按用户选择使用；冲突时说明具体冲突。
- 只分析时保持只读；用户要求修改时直接落实到指定工作稿。保持原稿或版本副本的方式服从当前任务，不为每轮修改制造大量备份。
- 区分文本格式整理、逻辑结构整理、技术内容修改。按授权范围执行；整理格式不顺手改写技术结论，整理逻辑不补造事实。

## 按当前阶段工作

### 1. MD 草稿与交互修改

读取 [Markdown 与逻辑格式规则](references/markdown-rules.md)。用户明确采用 Wings 代码讲解规范时，再读取 [Wings 项目规则](references/wings-profile.md)。

1. 阅读工作稿和相关参考，明确本轮要解决的问题及影响范围。
2. 在同一份工作稿上落实反馈，维护章节层级、模块内部顺序、术语、图注以及代码对应关系。需要改正文事实或代码逻辑时，只核对相关依据。
3. 修改后重读受影响的章节和上下文。只改格式时，对照正文、代码与链接确认没有语义漂移；调整结构时检查移动内容、编号及交叉引用。
4. 根据改动运行必要的 MD 检查；局部标点修改无需强制全套检查。简述已改位置与实质问题，避免每轮重新粘贴全文。
5. 不自动生成 Word、PDF、ZIP 或额外审阅报告。用户需要报告或问题较多时，再单独交付带章节或行号的问题清单。

只读自动检查：

```text
python <skill-dir>/scripts/check_markdown.py <工作稿.md>
```

需要落盘检查结果时加 `--report <检查结果.json>`；定稿检查可加 `--final`；要求本地普通链接全部存在时加 `--strict-links`。检查器不证明技术正确性，不检查网络链接可达性。

### 2. MD 定稿

- 用户确认定稿时，核查未处理批注、缺失图片、破损代码块及明确占位内容。对未解决事项如实说明，不自行补写为完成状态。
- 定稿不等于自动转 Word。根据用户要求保留现有文件，或生成明确命名的定稿副本。
- 后续仍可修改 MD；一旦正文变动，已有 Word 视为旧版本，按用户要求重新生成。

### 3. 用户要求转 Word

读取 [Word 排版与转换规则](references/word-rules.md)。使用用户指定版本或会话中已明确选定的 MD；参考模板只提供样式与版式，不带入旧正文。

1. 明确源 MD、输出位置、参考 Word 和必要的图片。已有会话决定直接沿用，横向末页、双版本和 ZIP 仅在用户需要时生成。
2. 以 MD 为内容基准转换。只调整 Word 样式、尺寸和分页；内容问题回到 MD 处理，并向用户说明实际改动。
3. 可用配套转换器处理常见技术 Markdown。运行前按 Word 规则核对支持范围和依赖；特殊结构可选择适合的工具，不静默丢弃内容。

```text
python <skill-dir>/scripts/build_word.py <定稿.md> --output <输出.docx> --template <参考.docx>
```

4. 对比章节顺序、正文、代码行、表格单元格及图片，检查 DOCX 结构；实际打开 Word 并渲染检查字体、溢出、代码折行、分页和页码。
5. 结构检查通过和实际渲染通过分别报告。环境无法渲染时说明尚未核验的项目，不把“导出成功”写成“版式已通过”。

## 交付

MD 阶段给出最新工作稿路径和必要的修改说明；Word 阶段给出 Word 路径、核验结果与实质限制。内容只在用户要求时增补；工具脚本只承担机械转换与检查。

本技能包含的工具及其选项、依赖见对应规则文件；脚本路径始终相对本技能目录，不依赖 Wings 仓库、历史文件名或内存目录。
